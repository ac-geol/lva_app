# Browser app

The engine from `core/`, running under Pyodide in a Web Worker. No server, no
upload, no network at run time — the page, the Python runtime and the data all
stay on the machine that opens it.

## Build and run

```bash
python scripts/build_app.py --pyodide    # once: fetches the runtime, ~34 MB
python scripts/serve_app.py              # rebuilds, then serves
# open http://127.0.0.1:8777/index.html
```

Use `serve_app.py` rather than pointing a plain server at `app/`. `core.zip` is
a snapshot of `core/`, so editing the engine and reloading serves the *old*
code — stale defaults, stale behaviour, and nothing on screen to say so. It
caught me twice. `serve_app.py` rebuilds on every start and sends no-cache
headers.

Nothing here is committed: `core.zip`, `pyodide/` and the sample CSV are all
build artifacts, regenerated by that one command.

## What is here

| path | what it is |
|---|---|
| `index.html` | The app. Six steps: drop a file, confirm the columns, pick the assay, check what arrived, set the parameters, estimate. The result carries two stereonets, the quality diagnostics and the Leapfrog export. |
| `worker.js` | Pyodide bootstrap and the message loop. A **module** worker — Pyodide 314 dropped classic workers, so it imports `pyodide.mjs` rather than calling `importScripts`. |
| `bridge.py` | The Python side: actions in, results out. Deliberately outside `core/`, exactly as `scripts/` and `viz/` are. Fetched rather than zipped, so it can be edited without a rebuild. |
| `core.zip` | `core/` verbatim. One source of truth with the tests — there is no second copy of the engine. |
| `viewer.js` | The 3D view. An ES module, because three.js only ships as one — it is imported separately and handed to `index.html` through `window`, and a failure to load hides the view rather than taking the result panel down. |
| `pyodide/`, `three/` | The Python runtime, the three wheels the engine needs, and three.js. Vendored for the same reason: the app has to run with no internet. |

## Protocol

`bridge.handle(action, payload_json)` returns a plain dict. Metadata is
JSON-ready scalars; bulk geometry is raw `bytes`, which Pyodide hands to
JavaScript as `Uint8Array` and the worker moves into the page by transfer
rather than copy.

Actions: `versions`, `preview`, `load`, `run`, `export`.

`versions` also returns the engine's own defaults, read straight out of
`DEFAULT_CFG`. The page never restates a default, so the controls cannot drift
from the engine they drive.

`preview` reads only the first 2,000 rows, so someone correcting a column
mapping is not waiting on a full parse to see whether the guess was right. It
accepts partial overrides — anything the user did not touch keeps
auto-detecting — and excludes already-mapped columns from the assay candidates,
since a column cannot be both the depth and the grade.

Errors never escape into JavaScript as exceptions. `handle` catches them and
returns `{ok: false, error, error_type, traceback}`, so a bad configuration
reads as a message rather than a dead worker.

Coordinates cross as float32 offsets from a float64 origin. Full UTM values
lose millimetres in float32 and make WebGL jitter; the float64 values never
leave Python except through the export, which is written as text.

## Verified against the CLI

The same sample file, the same config, x86-64 CPython against wasm32 Pyodide:

| | CLI | browser |
|---|---|---|
| rows / holes | 22,324 / 112 | identical |
| active nodes | 3,349 | identical |
| valid orientations | 2,017 | identical |
| vs drill pattern | 1.219337661095° | 1.219337661352° |
| true error | 15.900440855905° | 15.900440856120° |
| first exported row | — | byte-identical |

Worst relative difference on any float: **3.5e-10**, which is last-bit
arithmetic between two platforms, not a difference in behaviour.

## Two things the browser found

**The engine assumed a 64-bit platform.** `np.bincount` requires `intp`
indices, and `intp` is `int32` under wasm32. Every index array in
`core/neighbors.py` was explicitly `int64`, so the first real run raised
`Cannot cast array data from dtype('int64') to dtype('int32')`. Fixed by using
`np.intp` for anything that indexes an array, while packed composite keys stay
`int64` for range. `tests/test_vectorization.py` pins it; those assertions look
tautological on a 64-bit machine and are the only guard on a 32-bit one.

**Pyodide is vendored, not loaded from a CDN.** The CDN is exactly what a
locked-down or offline site network blocks first, and a runtime download would
quietly undo the property that makes this build viable — that nothing leaves
the machine.

## Stereonets

Equal-area (Schmidt) lower hemisphere, the same projection as
`viz/stereonet.py`, so a browser panel and a matplotlib figure of the same run
are the same picture. Two panels always: the chosen method, and the drill
pattern with the grades stripped out, drawn identically so they can be compared
by eye.

Density is computed by binning the poles into a grid and blurring it with a
separable Gaussian, rather than evaluating a kernel at every grid cell for every
pole. The naive form is grid x n and visibly stalls the page at a few thousand
poles; this gives the same picture in a fraction of the time.

The colour ramp is a single hue, light to dark. Its dark-mode steps are chosen
against the dark surface rather than flipped from the light ones, so density
gains contrast against whichever surface it sits on. Step 0 is each mode's
raised surface, which keeps the projected disc faintly visible where nothing
plots.

## The 3D view

Cheap for one specific reason: the engine already sends the unit normal of every
estimated plane, so orienting a disc is a single quaternion from +Z to that
vector. No trigonometry, no angle convention to get wrong, and no way for the
view and the Leapfrog export to disagree about what a plane is.

Discs are thinned by default (1 in 5). Downhole spacing is metres while a
legible disc is tens of metres across, so drawing every sample stacks them into
opaque coins and hides the very thing the view exists to show. The caption always
says how many of the total are drawn.

Colouring by **difference from drill pattern** is the diagnostic the whole view
is for: dark discs are where the answer is reporting the drilling rather than
the rock. A stereonet cannot show that spatially, and with `shape_pca` as the
default it is the failure mode worth watching.

## Reproducing a run

**Save settings** writes a JSON file carrying the assay column, any column
mapping the user corrected by hand, every parameter, the engine's package
versions, and the run's own diagnostics. **Load settings** puts the parameters
back. Only keys the engine currently exposes are read, so a stale file from an
older version cannot smuggle in a parameter that no longer exists.

The data file is not saved with it — it is the user's, and keeping it out is the
point of the whole design.

## The one unverified convention

Dip and dip azimuth are settled. **Pitch is not**: the direction it is measured
in has never been confirmed against Leapfrog, and a reversed pitch produces an
ellipsoid correctly oriented as a plane but with its long axis pointing the wrong
way inside it — which is exactly what LVA angle coding consumes.

`scripts/make_convention_check.py` writes 14 planes of known orientation, and
`docs/LEAPFROG_CHECK.md` says what to look for. The app says so too, in the
reference panel above the download, until the check is done.
